# 塔罗牌抽牌与 AI 解读

一个单页工具：**提出你的问题 → 用系统加密随机源抽牌 → 让 AI 解读牌面**。

抽牌和牌义全部在你本机完成，只有「解读」这一步会联网，发给你自己配置的模型。

双击 `index.html` 就能用，不需要装任何东西、不需要起服务器。

---

## 先读这一节：它不做什么

这一节比其他所有内容都重要。

**塔罗牌不预测未来，这个工具也不。**

抽牌的过程是**刻意切断**问题与牌面之间任何因果联系的程序——这正是「随机」的含义。牌面之所以常常让人觉得很准，机制是**巴纳姆效应（主观验证）**：笼统而普遍的描述，会被读的人自动补全成「说的就是我」。这一点从 Forer 1949 年的经典实验起就有证据：

| 发现 | 数字 | 出处 | 证据强度 |
|---|---|---|---|
| 同一份**通用**人格描述发给全班，学生普遍认为高度贴合自己 | — | [Forer 1949, *J. Abnorm. Soc. Psychol.* 44:118–123](https://psycnet.apa.org/doiLanding?doi=10.1037%2Fh0059240) | 同行评审实验 |
| 塔罗大阿卡纳分类与大五人格（IPIP）比对 | 494 名被试，**各类别间无显著差异** | [Santosa 2012, *ANIMA Indonesian Psychological Journal* 28(1)](https://journal.ubaya.ac.id/index.php/jpa/article/view/4183) | 同行评审量化实验 |
| 塔罗解读的盲测（真解读 vs 对照解读能否被区分） | 存在研究，但我们**未能取得全文核实** | Blackmore 1983, *JSPR* 52:97–99 | 仅书目记录 |
| 大模型在无依据时倾向于附和用户 | 谄媚率 **58.19%**，用户反驳后**持续率 78.5%** | [arXiv:2502.08177 (AIES 2025)](https://arxiv.org/abs/2502.08177) | 同行评审会议论文 |
| LLM 辅助塔罗的用户研究 | 12 位实践者访谈；明确指出查询与牌面**不存在因果关系** | [arXiv:2602.11367 (CHI '26)](https://ar5iv.labs.arxiv.org/html/2602.11367) | 同行评审，但为 n=12 定性研究 |
| 「塔罗解读 × 巴纳姆效应」的量化后续研究 | **未找到** | — | — |
| 心理学会关于占卜类应用的专门立场声明 | **未找到** | — | — |

**所以这个工具的定位是**：换一组陌生的符号，帮你说出你已经在想的事。它的价值在于「提供了什么角度」，不在于「算得准不准」。

**不要**用它替代医疗、法律、心理或财务上的专业判断。这一条不是形式化的免责声明：美国爱荷华州总检察长办公室曾对一名宣称能「疗愈」的占卜从业者签发合规保证书并处以罚款，背景是一名客户死亡（[执法文件](https://www.iowaattorneygeneral.gov/media/cms/AVC_executed_12_0412A0D2AA6E6.pdf)，[新闻报道](https://www.kcau9.com/news/iowa-news/iowa-medium-barred-from-advertising-healing-services-after-client-death/)）。

**还有一件事值得知道**：正逆位比例（默认各 50%）是**风格选择，不是规则**。塔罗圈内没有共识——一项社群投票里 38% 的人从不使用逆位，固定用一半的只有 1%（[投票](https://www.thetarotforum.com/forums/topic/16506-do-you-read-with-reversals-poll/)，社区自选样本，非代表性调查）。所以不要把「抽到逆位」当成某种必然的凶兆。

## 已知限制

- **牌义不可复现**：同一副牌跑两次，模型的说法会不一样（`temperature` 默认 0.8）。这不是 bug。想看稳定性就点「重新解读一次」对比。
- **贴合度分数只测「有没有提到」，不测「说得对不对」。** 一条解读可能完整回应了你的问题却给出糟糕的建议。它是筛子，不是裁判。
- **词表是有限的。** 问题里如果全是不在词表里的说法（比如很专业的行业词），贴合度会被低估。这种情况看分数旁边的「已回应 N/M」自己判断。
- **引文核对只管「有没有记错牌」，不管「说得对不对」。** 引文全部通过但推理平庸，是完全可能的。
- **模型有谄媚倾向**（前面引的研究：58% 的案例、被反驳后持续率 78.5%）。提示词里明确要求它不要附和，但无法根除。所以「这个解读最不确定的地方」那一栏要当真看。
- **长牌阵（凯尔特十字）的解读容易失焦**，模型可能把注意力集中在少数几张牌上。
- **历史记录不做云同步**，清掉浏览器数据就没了。
- **补充牌是可选的一步。** 补 1-3 张通常能起到「强调 / 修正」的作用；补十几张会让模型的注意力被摊薄，反而可能把原牌阵读得更浅。
- **挑牌顺序决定牌位归属**，所以挑之前要看清楚牌阵每个位置在问什么。挑错了只能重新洗一次（没有「反悔上一张」——因为牌一旦翻开就已经定了，撤销会让过程变得可以反复试探）。

### 还没在真实浏览器里手工验证过的

这一节值得认真读，因为**曾经有一个让整个页面不可用的 bug 就藏在这里**。

逻辑层面已经用真实 HTML 解析器 + 真实 DOM + 真实事件系统跑过整套交互
（`verify-browser.js`），但下面这些仍然只能靠人眼，**我无法自动验证**：

- `file://` 协议下直接连 HTTP API 时的 CORS 是否通过（取决于你的接口是否允许跨域）
- 抽牌翻转动画的实际观感与节奏
- 字体与配色在你的系统上的实际效果
- 窄屏（手机）下的排版

想快速看一眼版面，运行 `node preview.js` 会生成 `preview.html`，
里面把 6 种牌阵、补充牌和牌区全部渲染出来（用的是和真实页面完全相同的 CSS
与渲染代码），双击即可用眼睛检查有没有重叠、裁切、溢出。

如果你的浏览器有拦截行为，起一个本地服务器打开即可（`python -m http.server`）。

#### 那个曾经让页面完全不可用的 bug（以及为什么测试没抓到）

现象：**打开页面后点什么都没反应**。

原因在 CSS 里：

```css
.modal { position: fixed; inset: 0; z-index: 100; display: grid; }
```

浏览器自带的 `[hidden] { display: none }` 是**属性选择器**，特异性 (0,1,0)；
而 `.modal` 是**类选择器**，特异性也是 (0,1,0)，但它写在作者样式表里，
于是把 `display: none` 覆盖掉了。结果三个弹窗在页面一打开时就全部可见，
`position: fixed; inset: 0` 铺满视口叠在一起，把所有按钮都挡在下面。

**为什么 448 项断言一项都没抓到**：所有测试检查的都是 DOM 的**状态**
（`hidden` 属性、类名、子节点数），而这是**样式计算**的问题。
DOM 引擎不做 CSS 级联——`element.hidden === true` 完全成立，
但浏览器画出来的依然是可见的。

修法是加一条全局兜底：

```css
[hidden] { display: none !important; }
```

并新增了 `verify-css.js`（当时 19 项，后来扩充到 72 项）专门盯这类「状态对但渲染错」的问题：
它把 HTML 里所有带 `hidden` 属性的元素和 CSS 里给它们设 `display` 的规则对一遍，
还会检查 `render.js` 里算牌桌尺寸用的常量与 CSS 里的卡片尺寸是否一致。

**这个 bug 值得记住的教训是**：测试覆盖率高不等于覆盖到了对的东西。
448 项断言在这个 bug 面前是 0 项。

## 它是怎么工作的

```
提出你的问题
      ↓
  洗牌（本机，crypto 真随机）
      ↓
  背面朝上排开 ──→ 由你自己点选要哪几张
      ↓
  取牌义（本机，78 张牌的本地牌库）
      ↓
  发送给 AI ──→ 模型返回结构化解读，每张牌都要附一句引自牌义原文的话
      ↓
  引文核对（本机）──→ 把模型引的「原文」拿去和真牌义逐字比对
      ↓
  渲染到页面
      ↓
  看完了还想再问？→ 从同一副牌里继续补抽（不放回）
```

**哪些在本机、哪些会外发：**

| 环节 | 位置 | 说明 |
|---|---|---|
| 洗牌、排开牌区、选牌、定正逆位 | 本机浏览器 | 不上传 |
| 78 张牌的牌义 | 本机浏览器 | 不上传 |
| **AI 解读** | **你配置的模型服务** | **牌面 + 你写的问题会发送过去** |
| 引文核对 | 本机浏览器 | 不上传 |

用 Ollama 就一步都不出你的电脑；用 DeepSeek 就发给 DeepSeek。

## 自己抽牌：牌区是怎么做的

这个工具不替你抽牌。它只**洗牌**，然后把整副牌背面朝上排开，具体要哪几张由你点。

### 洗牌和摊开是两次独立的随机排列

这是整件事能否成立的关键。

- **牌序**（deckOrder）：决定桌上最终会出现哪些牌
- **摆放顺序**（fanOrder）：决定这些牌在牌区里从左到右、从上到下怎么摆

如果两者是同一个排列，那么「牌区第 1 张」永远等于「牌序第 1 张」，你点哪张结果都一样——「自己选」就成了走过场。分成两次独立洗牌之后，78 张牌出现在 78 个位置上的 78! 种组合等概率，**你选哪个位置是真实的随机输入**。

随机性因此有两个来源：`crypto` 的熵，以及你的选择。`verify.js` 里专门有两条断言盯着这件事：

```
牌序首位在牌区里出现过的位置数：78 / 78
固定挑第 0 位，抽到过的不同牌数：78 / 78
```

### 正逆位在你点下的那一刻才掷

不是洗牌时预设好的。这样「翻牌」在时间上也是真实的，而不是回放一段早就写好的结果。

### 挑牌顺序就是牌位顺序

先挑的落在牌阵的第一个牌位（比如三张牌的「过去」），第二张落在「现在」，依此类推。所以你在挑之前应该先看清牌阵每个位置在问什么。

### 牌区里看不到牌面

牌全部背面朝上，也不显示「第几张是什么牌」。整个牌区里不会出现任何牌名——这一条也有测试盯着，因为一旦泄露，「自己选」就失去了意义。

### 审计覆盖整段动作

一次「抽牌」在你看来是「洗牌 + 挑完所有牌」这一整段。所以审计记录从洗牌开始、到挑完才收尾，期间的取熵（每张牌的正逆位、每次重新摊开的位置）全部计入。牌桌下方显示的 `熵流偏移` 是连续的，说明用的确实是新取的熵。

## 随机性是怎么保证的

「完全随机」这句话在这个工具里是可以核查的，不是一句宣传。

### 做法

1. **随机源用 `crypto.getRandomValues`**（操作系统的密码学随机源），不用 `Math.random`。后者是可预测的伪随机。
2. **取样用拒绝采样，不用取模。** 直接写 `random % 78` 会因为 2³² 除不尽 78 而产生微小偏差（前若干个余数各多出现一次）。偏差大约 10⁻⁸ 量级，肉眼绝对看不出来——但既然「完全随机」是可以做到精确的目标，就没有理由不做到。拒绝采样让 78 个结果严格等概率。
3. **洗牌用 Fisher–Yates**，每一轮从 `[0, i]` 里等概率取一个交换过去，因此 78! 种排列严格等概率。
4. **每次抽牌都重新洗一副完整的 78 张牌**，抽完即弃。牌序不缓存、不复用，上一次抽到什么对这一次没有任何影响。
5. **洗两次**：一次决定牌序，一次决定牌区里的摆放顺序，两者相互独立（理由见上一节）。
6. **同一牌阵内不放回**，所以不会出现「过去和未来是同一张牌」这种自相矛盾的结果。
7. **正逆位独立掷 50%**，与抽到哪张牌无关，而且是在你点下那一张的瞬间掷的。
8. 你的问题文本**不参与随机数生成**。它只被记录和发送给模型，不影响抽牌结果。
9. **补充牌遵循同一套规则**：从同一副已洗好的牌里不放回地抽（或由你自己从牌区里挑），正逆位仍各 50% 独立掷一次，熵同样全部来自 `crypto`。追加动作不会让「这副牌是不是随机的」变得可疑——牌序在你按下第一次「洗牌」时就已经定好了，追加只是继续取剩下的。

### 怎么核查

`random.js` 提供审计记录：每次抽牌会记下消耗了多少个 32 位随机字、拒绝了几个、以及熵流的偏移量。这段信息会显示在牌桌下方，也写进导出文件。它的用途是：如果你怀疑牌被动过手脚，有据可查。

**追加抽牌也有自己的审计记录**，会接在原来的后面，例如：

```
本次消耗 80 个 32 位随机字，拒绝 0 个，熵流偏移 0，…；
补挑 1 张：本次消耗 77 个 32 位随机字，拒绝 0 个，熵流偏移 80，…
```

两次的「熵流偏移」是连续的（0 → 80），说明追加用的确实是新取的熵，而不是复用第一次的随机字。

### 实测数据

`node verify.js` 会跑真正的卡方检验（不是「看着挺均匀」）。下面是一次运行的实测值：

```
卡方统计量 = 83.42（自由度 77，0.05 临界值 98.0）   → 通过
逆位比例   = 49.76%（4 万次）                      → 通过
小范围卡方 = 4.15（5 格，自由度 4，临界值 9.49）    → 通过
洗牌后 78 张牌都可能当第一张（3 万次）              → 全部覆盖
牌序首位在牌区里出现过的位置数                      → 78 / 78
固定挑牌区第 0 位，抽到过的不同牌数                 → 78 / 78
```

最后两条是「自己选牌」这个功能的地基：如果摆放顺序和牌序有关联，它们会立刻掉下来。

这些数字每跑一次都不一样——这正是随机的表现，所以脚本判定用的是「小于临界值」而不是「等于某个数」。也因此它是偶尔会失败的：5% 的显著性水平意味着二十次里大约有一次会落在临界值之外。那一次不代表抽牌坏了。

## AI 解读是怎么做的

### 先解决「解读跟我的问题关系不大」

这是这类工具最常见的失败：你问了一件具体的事，它回你一段「这段关系需要更多的沟通与理解」。这样的句子删掉问题也成立，等于没说。

原因有两个，都要治：

**1. 只把问题整段丢过去。** 模型会把它读成一个「话题」，然后围绕这个话题说一通通用的话。所以现在会把问题**拆开**摆给它——在问哪件事、是不是一个二选一、你的顾虑是什么、有没有提到具体条件（几周、几年、多少钱）：

```
## 我的问题
原话：我现在的工作让我很疲惫，但又不确定要不要换。

这件事涉及的具体方面：现在、工作、疲惫
核心是：工作　←　每一条 reading 都必须出现上面这些词里的至少一个，并且真的在回应它

这是一个「要做选择」的问题。请明确说牌面支持往哪一边、依据是什么，不要只说「要多权衡」。
我提到的顾虑：又不确定要不要换
```

**2. 没有任何东西在事后检查。** 这是最关键的一环。现在会强制模型**先复述它理解的处境**，再解牌：

```
primer: 先用 2-3 句说明你从这个人的问题里读到的、他真正卡住的是什么。
        不要提任何牌，只谈他的处境。这是在证明你读懂了问题。
```

泛泛而谈的模型在这一步就会露馅——它没法在不理解问题的情况下写出具体的处境。你也会在页面上直接看到这段「模型对你这个问题的理解」，读一眼就知道它到底有没有懂你。

### 贴合度：把「答非所问」量化出来

解读回来之后，本地会做一次机械检查：把问题里的具体词（从一份领域词表里匹配出来的，比如「工作」「辞职」「孩子」「收入」）拿去每条解读里找，**一条都没提到的牌位会被标出来**，并在顶部给出一个 0-100 的分数：

```
82  问题贴合度 · 解读与你的问题对得上
```

或者：

```
28  问题贴合度 · 解读跟你的问题关系不大
    下面标了「与问题关系不大」的 2 条，内容换个问题也成立：行动（宝剑八）、结果（圣杯四）。
    另有 1 条出现了「多沟通」「相信自己」这类套话。
```

同时也会检测套话（「需要沟通」「相信自己」「顺其自然」「宇宙能量」等）。

**这个分数的诚实说明**：它只能测出「有没有提到」，测不出「说得对不对」。一条解读可能完整提到了你的处境却给出糟糕的建议——那需要你自己判断。但它抓到的那类问题（完全没提到）恰恰是最常见的。

分数档位的定义（`verify.js` 里用真实夹具测过）：

| 情况 | 大致分数 | 档位 |
|---|---|---|
| 每条都落到具体事情上 | 85-100 | 好 |
| 四条里有一条比较泛 | 55-75 | 一般 |
| 三条里两条是套话 | 20-40 | 差 |
| 三条全是套话 | 0-15 | 差 |

如果分数偏低，顶部会给两个按钮：**换个说法再解读一次**（模型有随机性，重跑可能更好），或者**回去把问题写具体**。

### 结构化返回

提示词要求模型返回固定字段的 JSON，而不是自由发挥的散文：

```
verdict     直接回答用户的问题，2-3 句。第一句就要给出判断或方向
cards[]     逐牌位：position / quote / gist（一句话摘要）/ reading（1-2 句补充）
actions[]   2-3 条可以真的去做的事
```

字段固定才能分区渲染，也才能机械校验。解析层能容忍模型加代码围栏、加「好的这是解读：」这类前缀、或者 `actions` 写成换行字符串。

**字段从六个减到三个**，这是为了治两个毛病。早先的结构是
`primer`（复述它理解的处境）/ `overview`（总览）/ `cards` / `synthesis`（串起来）/
`actions` / `watchOut`（最不确定的地方），问题在于：

- `primer`、`overview`、`synthesis` 三者内容高度重叠，都是「整体说明」，加起来上千字；
- `watchOut` 被要求「不要写没有」，于是只能生成套话；
- 每张牌还各带一句 `action`，十张牌就是十条建议，多数是凑数。

结果是凯尔特十字一次要读 2800 字，重点被埋在中间。用户的原话是
**「看着好累好复杂，而且没什么参考价值」**。

现在的 prompt 里写死了三条约束，都是为了同一个目标：
**允许留白**。每张牌只讲它自己额外提供的东西，没有额外信息就写
「与结论一致，没有额外提示」——硬给每张牌编一个独特含义，只会稀释真正的重点。

**仍然兼容旧结构**：历史记录里存的是六个字段的形状，
`normalizeReading` 缺 `verdict` 时会按 `overview` → `primer` + `synthesis`
往回找，每张牌缺 `gist` 时会从 `reading` 截第一句补上。

### 引文核对（这个工具最值得看的部分）

提示词要求模型为**每个牌位**附一句 `quote`，内容必须从该牌的牌义原文里**原样摘取**。然后本地把这些引文拿去和真正的牌义逐字比对，对不上的标红。

**为什么不信任模型自己的牌义记忆**：塔罗解读里最常见的错误不是结论不好，而是把牌记串了——比如把「宝剑八」的自我设限说成「宝剑九」的焦虑。要求引用原文能显著减少这类错误，而本地的逐字核对能把剩下的抓出来。

顶部会显示 `引文核对 3/3` 这样的比例。**这个数字比解读本身更值得先看**：如果模型编造了原文，它那一段的推理也不可信。

校验会拦住这些伪造手法（`verify.js` 里有专门的对抗测试）：

- 把两段话拼起来当引文
- 改写措辞、换同义词
- 颠倒语序
- 凭印象创作（「命运的车轮正在为你转动」这类）
- 引用**另一张**牌的原文
- 只给几个字的敷衍引文

而它容忍这些无害差异：去标点、加空格、全半角差异。

### 提示词里的边界约束

每一条都对应一个具体的失败模式，不是客套话：

- **不要复述牌义**——否则模型会把牌义抄一遍当解读
- **不要断言第三方的想法**——塔罗最容易被滥用成读心术
- **不要给具体时间、金额、姓名**——这类无法证伪的细节
- **不要替你决定医疗、法律、投资问题**
- **明确声明塔罗没有预测力**
- 牌面整体偏负面时不粉饰，但也不制造恐慌

## 怎么打开

**桌面上已经有一个「塔罗牌」快捷方式**，双击即可。

它指向 `launch-tarot.cmd`，而不是直接指向 `index.html`。这么绕一层是有原因的：直接把 `.html` 交给系统时，Windows 会转给「默认浏览器」，如果浏览器已经开着，它只是新开一个标签页、窗口不弹到前面，看起来像没反应。启动器显式调用浏览器并加 `--new-window`，双击必然弹出一个新窗口。

启动器会按顺序找 Edge 和 Chrome（几个常见安装位置），都没有才退回交给系统默认程序。它只做这一件事，找不到 `index.html` 会明确报错并暂停，不会静默失败。

> 启动器是**纯 ASCII** 的。`cmd.exe` 用系统 ANSI 代码页（中文 Windows 是 GBK）解析批处理文件，里面写 UTF-8 中文会变乱码——所以它的提示信息是英文的，应用本体（UTF-8）不受影响。

**图标**是用 `make-icon.py` 画出来的（纯 Pillow，不需要任何素材文件）：深紫圆底 + 金色四角星 + 细金环，和页面同一套配色。ICO 里有 16 到 256 共 7 档尺寸，桌面、任务栏、Alt+Tab 各取所需。想换图标就改那个脚本再跑一次：

```powershell
python make-icon.py
```

**移动过文件夹的话**快捷方式会失效（它记的是绝对路径）。重新指一下即可：

```powershell
$dir = "新的路径\tarot"
$shell = New-Object -ComObject WScript.Shell
$sc = $shell.CreateShortcut("$([Environment]::GetFolderPath('Desktop'))\塔罗牌.lnk")
$sc.TargetPath = "$dir\launch-tarot.cmd"
$sc.WorkingDirectory = $dir
$sc.IconLocation = "$dir\tarot.ico,0"
$sc.Save()
```

## 手机上怎么用

界面是响应式的，手机浏览器直接打开就能用。**也可以打包成 Android APK 装到手机上**，
见 [`android/README.md`](android/README.md)。仓库里不存二进制——去
[Releases](../../releases) 下签好的 APK，或者照那份文档自己打一个（产物约 280 KB）。

几个关键差别：

| | 桌面 | 手机 360px |
|---|---|---|
| 牌面尺寸 | 104 × 166 | 56 × 89 |
| 牌桌基准宽 | 900 | 302 |
| 待挑牌一行 | 11 张，78 张排 8 行 | 5 张，78 张排 16 行 |
| 待挑牌的尺寸 | 68 × 108 | 44 × 70 |
| 凯尔特十字桌面 | 900 × 920 | 302 × 539 |

**待挑的牌按网格排开，每张完整可见、互不压盖。** 这里曾经是「弧形 + 重叠」的扇形，靠每张只露 22px 把 78 张塞进两行。手机上那个设计不成立——牌面本来就小，一重叠就分不清哪张是哪张，点起来全靠猜。改成网格之后边界清楚，代价是要滚。

牌的大小由 `computeMetrics` 按牌桌宽算，并设了触控下限：触摸设备的牌不小于 44px，否则手指点不准。

**尺寸只有一个来源。** 全部由 `render.js` 的 `computeMetrics(视口宽, 是否触摸)` 算出，再写进 CSS 变量（`--card-w`、`--caption-w`、`--card-title` 等），CSS 只消费。早先 JS 里写死 `CARD_W=104`、CSS 里写死 `--card-w:104px`，两处靠一条测试比对来保持一致——手机适配需要两套尺寸，那种做法立刻就走样。

窄屏的媒体查询只管**排布和留白**（内边距、按钮高度、单列牌阵），不碰尺寸。两边都改尺寸就会出现「JS 按 56px 的牌算了坐标、CSS 却把牌画成 104px」这种错位。

### 这些数字怎么验证的

`verify-layout.js` 会对 **6 种视口**各跑一遍全部排版检查（手机 360/390/430、平板 768、桌面 1280/1440），每个视口都验：

- 所有牌阵（含补充牌）的牌面与牌位名互不压盖
- 所有内容都在牌桌范围内，没有被裁掉
- 待挑牌在同一行内不重叠，每张完整可见
- 基准宽不超过「视口减各层内边距」——算大了最右一列的牌会被裁掉

这不是形式主义——它当场抓出两个**只在窄屏出现**的 bug：

1. **五张牌阵的「根基」横向越界**：x=6，在 336px 桌宽下牌的左边缘算到 -5px。
2. **补 15 张有 24 处重叠**：`.slot-caption` 宽度写死 120px，而手机上牌只有 56px 宽——牌位名比牌还宽，相邻两张就压在一起。

这两个在 900px 基准宽下全都正常。只测一种尺寸的排版测试永远发现不了。

### 关于打包成 App

想做成 APK / iOS 安装包，需要 Android SDK + JDK（约 700MB~1GB）。这台机器上目前没有，但网络可达、磁盘够。

**一个坦诚的限制**：即使打包成功，我也**无法在这里验证 APK 能不能跑**——没有 Android 设备、没有模拟器、没有 adb。我能验证的只有「编译成功、包结构完整、资源打进去了」。「装到手机上能打开、能抽牌」这一条只能由你装上后反馈。这和之前 Edge 起不来是同一个边界：进程级的验证我做不了。

所以建议的顺序是：**先在手机浏览器里试，确认交互顺手了再打包**。把一个没在真机上验证过的交互固化进安装包，改起来更费事。

## 用法

### 1. 配置接口

点右上角「⚙ 接口设置」，填三样：**接口地址**（Base URL，要带 `/v1`）、**模型名**、**API Key**。

支持任何 OpenAI 兼容接口，有预设可选：

| 服务 | Base URL | 模型名示例 |
|---|---|---|
| **DeepSeek**（推荐） | `https://api.deepseek.com/v1` | `deepseek-chat` |
| OpenAI | `https://api.openai.com/v1` | `gpt-4o-mini` |
| Kimi | `https://api.moonshot.cn/v1` | `moonshot-v1-8k` |
| 通义千问 | `https://dashscope.aliyuncs.com/compatible-mode/v1` | `qwen-plus` |
| Ollama（本机，不出网） | `http://localhost:11434/v1` | `qwen2.5:7b` |

点「测试连通性」确认能通。配置存在浏览器 localStorage 里，本机 Ollama 不需要 Key。

**如果接口不支持 `response_format`**：程序会自动去掉这个参数重试一次，你不用管。

### 2. 提出你的问题

问什么都可以。这个工具**不评价问题好不好**，只把「这样问会怎么被读」说清楚：

| 你写的 | 它会怎么读 |
|---|---|
| 二选一（「要不要换工作」「该不该辞职」） | 拆出关键词，明确说牌面支持哪一边 |
| 是非判断（「继续和她打游戏可以增加好感吗」） | 给出明确判断和依据，不用「因人而异」推回来 |
| 具体的事（「我和他的状态，下一步怎么走」） | 拆出关键词，解读逐条扣住它们 |
| 开放的问题（「我今天会发生些什么」） | 把牌读成**此刻处境的映照**，指出什么值得留意，而不是预告会发生什么 |
| 留空 | 按「我当下最需要知道什么」来读 |

**开放问题不是「问得不好」。** 它是塔罗的传统用法之一。这个工具会专门告诉模型：不要写「可能会有意外的消息」这类无法证伪的预告，而要结合牌位本身在问的角度，指出此刻值得留意的方向。解读出来后还会检查有没有滑向事件预告。

如果问题写得够具体，输入框下面会列出解读将围绕哪些点展开：

```
解读会围绕这些点展开： 工作  疲惫  换
你这是一个「要做选择」的问题，解读会明确说往哪边、依据是什么。
你提到的顾虑：又不确定要不要换
```

唯一会提醒你的是**短到看不出在问什么**（比如只写「嗯」）——那时补一句具体在纠结什么会好很多。

> **它靠什么判断？** 词表 + 句式，不是语义理解。
>
> 句式这一条很关键：**句子形式本身就带信息。**「该不该」「要不要」「可以…吗」
> 这类是非问句必然指向一件具体的事，即使词表一个词都没抽到，也不该被当成
> 开放问题。这是被一个真实误判补上的——「我现在继续和她打游戏可以增加好感吗」
> 曾经因为词表里没有「游戏」「好感」而被标成「这是个开放的问题」。
>
> 词表覆盖常见领域（关系、工作、钱、身心、决定），其中不少日常互动词
> （游戏、好感、聊天、见面、回复……）都是被真实问题补上去的。**词表漏掉
> 一整片日常词汇，就会有一整类具体问题被误判成开放式**——所以它按需增长，
> 而不是一次设计到位。

### 3. 选牌阵

**牌阵决定抽几张**——每个牌阵有几个牌位，就要挑几张牌。面板上会写明：

> 这套牌阵要抽 3 张。先挑的牌落在第 1 个位置，所以挑之前先看清每个位置在问什么。

| 牌阵 | 张数 | 什么时候用 |
|---|---|---|
| 单张牌 | 1 | 一个具体的小问题，只想要一句直话 |
| 三张牌 · 时间流 | 3 | 过去 / 现在 / 未来。看一件事怎么走到今天 |
| 三张牌 · 现状行动结果 | 3 | 最实用。已经知道问题，需要具体动作 |
| 五张牌 · 小十字 | 5 | 三张看不清时用，多出「阻碍」和「环境」 |
| 关系牌阵 | 6 | 两个人之间：各自状态、彼此期待、关系走向 |
| 凯尔特十字 | 10 | 最完整的经典牌阵，解读最长 |

**牌库**可以选完整 78 张，或只用 22 张大阿卡纳（问题更偏向人生课题）。

### 4. 洗牌，然后自己从牌区里挑

点「洗牌」。整副牌会（用系统加密随机源洗过之后）背面朝上按网格排开。

**挑哪张由你决定。** 牌阵要几张就挑几张：

```
请挑第 3 张（共 10 张），牌区里还剩 76 张。
```

上面会列出你已经挑走的牌，牌会从牌区里消失。挑满之后牌区自动收起，牌按**挑取的先后顺序**落到牌阵的各个牌位上——先挑的落在第一个位置（比如三张牌的「过去」）。

所以挑之前先看清牌阵每个位置在问什么（牌阵卡片和牌位名上都有写）。

点任意一张牌可以看它的完整牌义（正位和逆位都列出来）。**如果你觉得朝向不对，可以在弹窗里手动翻转**——但请注意：这会让之前的解读作废（牌面和解读必须一致），而且这个动作会明确提示你，不做任何伪装。

### 5. 生成解读

点「生成 AI 解读」，等 10-40 秒（牌阵越大越慢）。

结果按这个顺序呈现：

```
结论          ← 直接回答问题，多数人只需要读这一段
可以去做的事   ← 2-3 条具体行动
每张牌说了什么  ← 收起状态每条一行摘要，点开看引文与详细解读
───────────
问题贴合度     ← 以下是事后核对用的元信息，不抢注意力
引文核对
```

顺序是刻意的：**先给答案，再给做法，细节折叠，核对信息垫底**。
牌少于四张时（单张牌阵、三张牌阵）自动展开——本来就短，全部收起反而多一次点击。

可以「导出为文本」，也可以「重新解读一次」看看模型换一次会不会说得不一样——**这本身就是一个有价值的检验**：如果两次解读差别很大，说明这次牌面对应的问题本身就不清晰。

### 6. 补充牌：看完再补几张

牌桌下方有个「看完之后想再补几张？」的选择器，选好张数点「抽补充牌」，就能在已经抽好的牌面上继续追加。

**追加的牌是从同一副已经洗好的牌里继续抽的，不放回。** 这一点是这个功能唯一说得通的做法：如果重新洗一副，就可能抽到桌上已经有的牌——桌上摆着「命运之轮」，追加时又出现一张「命运之轮」，那次解读就没法看了。所以抽牌结果里保存着整副牌洗好后的顺序，追加时从剩下的牌里接着拿。

补充牌在牌面上有明确的视觉区分：**金色边框**，牌位名旁边标着「补充」。

它们会被当成**对整体的补充与修正**送进提示词，而不是牌阵里的正式牌位。给模型的原文是这样写的：

> 用户在看完整套牌之后，主动要求再补一张。请把它读成对整体解读的补充、强调或修正：它印证了哪一部分？又补充了什么前面没提到的角度？不要把它当成牌阵里的一个独立牌位。

两个需要注意的行为：

- **抽补充牌会让已有的解读作废。** 解读是绑定在一组具体的牌上的，悄悄多出几张牌却继续显示旧解读，你会以为那段解读已经考虑了新牌——这比让你多点一次「生成解读」糟得多。所以程序会清掉旧解读并明确提示。
- **补充牌会写进历史记录和导出文件。** 重新载入那次牌面时，补充牌会一起还原，并且还能继续往下追加（牌池由「完整牌库 − 已抽的牌」重建）。

上限是牌库的总张数：一副 78 张的牌最多能全抽完；抽完后按钮会自动禁用，并说明没有可以追加的牌。

### 7. 历史记录

右上角「历史记录」里存着最近 50 次抽牌（只在本机浏览器）。可以重新载入某次牌面再生成解读。记录只存牌和问题，**AI 解读正文不保存**——需要留档就用导出。

```bash
node verify.js           # 牌库 / 牌阵 / 洗牌与挑牌 / 位置与牌面独立性 / 随机性检验
                         # / 引擎层面的张数控制 / 问题拆解与贴合度 / 引文核对对抗测试
                         # / JSON 解析容错 / DOM 布局与 XSS / 导出文本 / 提示词完整性
                         # / mock 服务真跑 HTTP
node verify-ui.js        # 用 DOM 替身把页面点一遍：洗牌、从牌区挑牌、切牌阵、
                         # 翻牌、历史记录、生成解读的成功与失败路径
node verify-browser.js   # 用真实 HTML 解析器 + 真实 DOM + 真实事件系统
                         # 加载 index.html、按顺序执行 <script src>、派发真实点击事件
node verify-css.js       # CSS 静态检查：[hidden] 是否真的生效、花括号配平、
                         # JS 里的卡片尺寸常量与 CSS 是否一致
node verify-layout.js    # 像素级排版：把坐标和尺寸还原成矩形，检查所有牌阵
                         # （含补充牌排成多行）有没有互相压盖或被裁掉
node verify-extreme.js   # 极端情况：把完整回复切在 19 个不同位置模拟截断、
                         # 11 种畸形 JSON、15 种结构异常、10 种 HTTP 异常、
                         # 8 种奇怪输入（超长/emoji/控制符/JSON 注入）
                         # 判定标准：不许崩，且结果必须有意义
node preview.js          # 生成 preview.html，用眼睛检查牌阵、补充牌、牌区的版面
```

合计 **1814 项断言**，全部不需要网络。

每个套件末尾都有一条「断言数不低于基线 N」的守卫。这不是形式主义：
文件里有多处 `if (xxx) { …若干条断言… }`，条件不成立时整块会被跳过，
而套件仍然打印「全部通过」——只是数字悄悄变小。本项目踩过这个坑
（8 条断言静默失效，靠「测试数怎么没变」才发现）。
**加了新断言就把对应文件里的基线改大**；它变小，就说明有东西被跳过了。

### 五个测试文件为什么不能合并

它们的「可信度」和覆盖的层次都不同，这是刻意的：

| 文件 | 用什么跑 | 能抓到什么 | 抓不到什么 |
|---|---|---|---|
| `verify.js` | 纯 Node | 随机性、算法、提示词、HTTP 链路、坐标距离 | 真实的像素渲染 |
| `verify-ui.js` | **我自己写的** DOM 替身 | 状态流转、事件绑定、异步时序 | 我对 DOM API 的理解错误（替身会跟着我一起错） |
| `verify-browser.js` | 真实的 domino DOM 引擎 | 真实的 DOM API 用法、脚本加载顺序、XSS | **CSS 样式计算** |
| `verify-css.js` | 静态分析 styles.css | `[hidden]` 失效这类规则冲突 | 布局好不好看 |
| `verify-layout.js` | 坐标 × 尺寸 → 矩形 | **元素互相压盖、被裁掉** | 字号、配色、间距美感 |

第四行那个「抓不到什么」曾经害过一次：`.modal { display: grid }` 盖掉了
`[hidden] { display: none }`，三个弹窗在页面加载时全部可见，把整页按钮挡住。

第五行是后加的，起因是另一个真实 bug：**牌位名被下面那张牌压住**。牌位名画在
牌下方（约 40px 高）且比牌面还宽（120px vs 104px），而当时的纵向间距是按
「牌高 166px」算的。前三套测试都看不见这个问题——它们查的是坐标距离和 DOM
状态，不会把「坐标 × 尺寸」还原成矩形。

### 用真实 API 自检

配好 Key 之后想确认整条链路能通（**Key 不会出现在命令行历史里**）：

```powershell
$env:TAROT_KEY='你的Key'
node check-live.js
Remove-Item Env:\TAROT_KEY
```

它会依次做：连通性测试 → 真抽一次牌并请求解读 → 打印解读与引文核对结果 → 导出成 `live-check-output.txt`。费用约 2 次调用。

可以换自己的问题和牌阵：

```powershell
$env:TAROT_SPREAD='celtic-cross'
$env:TAROT_QUESTION='我要不要搬去另一个城市？'
```

### 关于 `.domtest/`

里面是 [domino](https://www.npmjs.com/package/domino)（BSD-2-Clause 许可，**零依赖**的
DOM 实现），从 npm 下载后直接解包存放，956 KB。

之所以随仓库带着而不是写进 `package.json`：这个项目刻意做到「一个依赖都不装」，
双击 HTML 就能用。为测试引入 npm 会让「不用装任何东西」这句话失效。
如果你不想保留它，删掉 `.domtest/` 即可——只是 `verify-browser.js` 会跑不了，
另外两个测试不受影响。

## 改这个项目时要注意的两件事

**1. 不要在 PowerShell 里用 `Set-Content` / `Out-File` 改这些源文件。**

开发过程中我这么做了一次，`Set-Content` 默认按 ANSI 编码写回，
`js/app.js` 里 107 处中文当场变成乱码，文件直接报废（源码里全是中文注释和
牌义文本，这类损伤是静默的——PowerShell 不会报错）。用编辑器改，
或者用 Node 的 `fs.writeFileSync(file, text, 'utf8')`。

改完可以这样自检编码：

```powershell
node -e "const s=new TextDecoder('utf-8',{fatal:true});const fs=require('fs');const b=fs.readFileSync('js/app.js');const t=s.decode(b);console.log('替换字符:',(t.match(/\uFFFD/g)||[]).length)"
```

输出 0 才算正常。

**2. 改完 `js/` 或 `styles.css`，都要重跑四套测试。**

`verify-browser.js` 尤其重要——它是唯一能发现「脚本加载顺序错了」或
「用了一个实际不存在的 DOM API」的测试。而 `verify-css.js` 是唯一能发现
「DOM 状态对、但浏览器画出来是错的」的测试。
